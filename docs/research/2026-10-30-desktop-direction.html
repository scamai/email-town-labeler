02 / 原因

“标签难用”同时来自平台差异和分类噪声。

Gmail 标签、Microsoft 邮箱的 categories（分类）以及普通 IMAP 邮箱并非同一种对象。Gmail 提供自己的 IMAP 扩展；Microsoft Graph 可以同步消息、设置分类，但显示颜色仍依赖客户端。把一个 Google 标签写回去，并不能保证它在所有邮件软件里都以相同方式出现。具体 Outlook 版本和账户类型尚未确认，不能把旧版 Outlook 的限制一概套用。平台依据

在 Gmail 手机应用里添加另一家邮箱，也不意味着那个邮箱已经成为 Gmail API 能读取的 Google 邮箱。Google 官方说明：Gmailify／网页端 POP 代收在 2026 年第一季度后不再接纳新用户，老用户可用至 2027 年 1 月；手机应用仍可用 IMAP 接入。新产品不宜把“先汇总进 Gmail”作为必要前提。Google 说明

模型也有边界。模型卡的 87.3% 来自方法评估中 2,101 封留出邮件，与原工具标签比较；不是最终发布权重在新用户上的准确率。推荐策略下“需要处理”的召回率为 0.88、精确率为 0.41，取舍是少漏掉重要邮件、多产生提醒。训练邮件来自一人的英文收件箱；中文、多账户及不同职业场景的效果未测。评估口径

设计推断：统一界面要给人清楚的分类、快速纠错和完成状态；仅把所有“需要处理”堆在一起，可能增加负担。“已处理”应与“分类错了”分开，避免把完成任务误当成模型训练标签。

03 / 方案取舍

统一分类工作台最贴近当前问题，但应与现成客户端比较。

选择能解决什么主要代价与判断
Apple Mail／Thunderbird已有多账户统一收件箱、阅读和回复。采用成本最低，应作为基线；它们并未自动接入本项目的统一分类与学习。若只是少切换账户，可能已经足够。
菜单栏控制面板登录、状态、开关、模型下载和错误提示。相对小，但邮件仍分散；只能作为产品的一部分。
分类工作台（推荐验证）跨账户分类列表、预览、纠错、已处理，跳转原邮箱。需要多账户同步和展示层；能复用现有引擎，控制范围后较适合个人项目。
完整邮件客户端完整阅读、撰写、附件、草稿、搜索、离线和收发。长期维护面广，且发送、归档等涉及改变现有产品边界。等工作台收益明确后再评估。

窄屏表格可左右滑动。读法：成本是范围上的定性推断，不是已报价的工期。现成客户端能力见 Apple Mail 与 Thunderbird 官方介绍。这些方案尚未在用户的实际账户组合中比较。

浏览器扩展能改善某个网页界面，但需要分别跟随 Gmail／Outlook 页面变化，也不直接提供跨服务的统一数据层，因此不作为首选。若只想改善一个网页，结论可能改变。

04 / 建议的第一版，尚未实现

第一版应完成“发现 → 判断 → 处理”的一个闭环。

  • 一个列表：所有账户的“需要处理”、订阅、订单、旅行等统一分组；显示来源账户、主题、发件人和同步时间，支持按账户筛选。各账户仍各自拥有邮件，不做邮箱迁移。
  • 三个关键动作：查看简短预览、改分类、标记已处理；明确显示低置信度。需要回复时打开原邮箱对应邮件；精确跳转必须实测，不支持时提供可理解的替代路径。
  • 一个状态入口：授权过期、离线、模型下载、暂停和恢复都有可见状态；电脑睡眠期间不承诺持续分类。

技术上建议保留 Python 分类与学习引擎，增加独立的账户管理和连接器接口；macOS 优先时可验证 SwiftUI 界面与受控本地工作进程的组合。如果明确需要 Windows／Linux 同步发行，再比较跨平台桌面外壳。安装打包、进程恢复和模型共享必须先做小型技术验证，尚未证明当前程序可直接装进沙盒。

读取先通过 Gmail API，下一步按实际账户需要接 Microsoft Graph（Outlook.com／Microsoft 365），普通 IMAP 再按需接入。在 Outlook 客户端里看到一个 Gmail 账户，并不表示该账户应改用 Graph。Graph 的增量同步及分类接口已有官方支持；企业租户的授权政策仍需实际测试。接口依据

统一分类应以本地语义为基础，再按能力选择性写回 Gmail 标签／Microsoft 分类；不要为了显示分类就把普通 IMAP 邮件移动到文件夹。反馈同步要避免把自身写回当成用户纠错，并保存人的修改优先级。

隐私设计变化必须讲清楚：当前数据库不保存主题和正文。工作台需要显示邮件，可先按需读取并在内存中短期缓存；若增加持久索引、离线正文或全文搜索，就要重新定义保留期限、清除、加密和退出账户的行为。凭据放入系统钥匙串；正文预览要限制活动内容与远程资源。不能继续沿用“完全不存邮件内容”的承诺而悄悄加入缓存。

05 / 发行可行性

可发布 Mac 软件，但授权与安装体验是独立工作。

建议先自用验证，再提供签名并公证的直接下载安装包，最后判断 Mac App Store 是否值得。Apple 允许商店外分发；商店要求沙盒。现有 Python 依赖、模型下载、后台进程、升级与回滚、Apple Silicon／Intel 支持，都要在目标机器验证。此建议不是“打包即可上架”的承诺。Apple 分发说明

普通用户不应被要求自行创建 Google Cloud 项目。公开应用若请求 Gmail 受限权限，通常需要 OAuth 审核；纯本地运行并不自动豁免。若让受限邮件数据经过第三方服务器，还涉及安全评估。个人使用和特定内部使用有例外，不能直接套到公开发行。Google 审核说明

已有 v0.1.0 资产是 Python 安装包及模型包，不能当成上述桌面发行已经完成的证据。近期优化多列在 Unreleased 下；后续要让版本号、变更记录和可下载包对应起来。PyPI 名称还被无关项目占用，桌面产品的名称及发行渠道需要明确。

06 / 下一步与排序

先验证统一处理的价值，再投入更多平台与发行工作。

唯一的下一步：项目维护者组织多账户工作流验证。下一轮开始时确认常用邮箱类型及手机需求，先比较现成统一收件箱，再验证工作台原型。完成标准：用户能在同一列表找到、判断并完成跨两个账户的待处理邮件，纠错不跨账户、断网和重新授权后可恢复，并能回到正确原邮件。建议连续自用一周后复盘；这是验证窗口，开发工期与启动日尚未承诺。

  1. P0 · 账户基础和最小工作台：两 Gmail 账户隔离、消息身份带账户、独立同步游标和凭据、不会覆盖彼此的后台管理；共享模型资源；列表、预览、纠错及完成状态。这一步仅验证多账户基础；若实际痛点是 Gmail 加 Microsoft 邮箱，必须完成下一步后才能判断跨服务收益。
  2. P1 · 第二类邮箱：若用户常用 Microsoft 邮箱，加入 Graph；确认企业租户可授权，真实测试分类和重新同步。其他服务按实际账户排序。
  3. P1 · 使用质量：检查“需要处理”的误报／漏报；加入明确授权的个人评估集及中文样本，分别按账户和语言统计。先调阈值与反馈体验，再决定是否训练新模型。
  4. P2 · 小范围发行：免命令行安装、OAuth 审核方案、钥匙串、签名公证、卸载与清理、版本更新与回滚；先确认冷启动和长期常驻资源表现。
  5. P3 · 后续按证据决定：普通 IMAP、离线全文搜索、手机端、即时推送、完整微调或完整收发。它们不是现阶段统一工作台的先决条件。

以上是本次新增建议，不是仓库既有承诺。用相同的代表性处理任务，对照现成客户端和工作台，记录切换账户次数、处理耗时、误报／漏报及每日主动使用情况，当前均未测量。只有在减少操作负担且未增加重要邮件遗漏时，才继续扩展；具体可接受阈值由用户在试用前设定。若现成客户端已经解决主要问题，优先保留引擎并改善安装；若必须在手机和电脑同时操作，就重新评估本地状态同步的成本。

07 / 边界

技术证据充足，用户收益与新产品运行仍未验证。

本次没有构建桌面应用、连接 Outlook／IMAP、进行公开发布或重新训练模型。现有测试的端到端场景使用内存假 Gmail，不是真实跨服务测试。本机服务状态检查只能证明检查时的运行与最近轮询，不能证明全部邮件分类正确或长期稳定。测试跳过项和历史测量在下方明确列出。

尚不清楚用户的账户数量、提供商组合、企业登录限制、中文比例、手机和离线要求。暂按 macOS 优先、个人使用、多个独立邮箱评估。没有用户访谈、商业需求验证、预算估算或确定工期。

未进行失败的产品实验；不选完整客户端与浏览器扩展是基于范围的取舍，并非实测失败。检索 Apple 的部分文档端点失败后改读官方分发说明，未以检索失败推断平台能力不存在。

08 / 研究方法

结论来自代码盘点、测试、运行状态和官方平台文档。

  1. 阅读 README、设计、架构、模型卡、配置、状态存储、后台服务及最近提交；独立只读代理核对现有能力与计划。
  2. 搜索本仓库计划文件与缺项文字，并查询开放 GitHub issues、release 和基线 CI；未找到开放 issue 不代表外部任务系统没有计划。
  3. 运行本地 pytest、ruff lint／format；读取已安装服务的脱敏状态，不触发回填或标签修改。实际账户、邮件内容和使用统计不写入本报告。
  4. 核对 Google、Microsoft、Apple 官方能力、权限与发行要求；以 Apple Mail／Thunderbird 的统一收件箱作为替代方案。
